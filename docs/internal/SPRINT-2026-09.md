### 2.1 The one step that stays with you — and Option B if you want it automated anyway

Why the apply is not automated by default:
1. **The failure that matters has no automatic rollback.** If 307 stops block production, no extrinsic can be applied, so the 306-as-308 `set_code` rollback is unreachable; recovery is stopping all five validators, restoring the pre-upgrade databases and re-authoring — manual, delicate, and not something to discover at 04:00 with nobody awake.
2. **Your own rule:** no upgrade inside 48 hours of the meeting, and never mid-era while the #164 run is measuring. A timer cannot read the meeting date.
3. **Provenance.** The agency will ask who reviewed the runtime that runs the chain. A human reading the `spec307 → master` diff before pressing apply is the answer; a timer is not.
4. **Time.** Writing and testing an arming script tonight costs more than the hour it saves tomorrow.

**Option B — armed upgrade timer (only if you accept 1–4).** You, on prod, tonight: a user timer `scalar-upgrade-gate.timer` at a UTC time you choose, running a script that proceeds only if every check passes and otherwise exits and emails/SMSes you: master head has all nine checks `success` (`gh api repos/…/commits/<sha>/check-runs`); the merge commit's PR carries the three PASS review comments; prod rebuilds the wasm from that commit and its sha256 equals the hash lab published to the evidence repo for rehearsal B; all five validators healthy, finality within 5 blocks, keeper timer active; current era not due to settle within 200 blocks; `~/econ-*.log` shows the #164 run idle or between eras; backup from step 5 exists and its sha256 verifies; `~/ARM-UPGRADE` exists (you create it to arm, delete to disarm). Then `apply-upgrade.mjs`, verify 307 and 20 blocks with finality, restart the three products, smoke; on verification failure **with blocks still advancing** apply rollback-308 and verify; on a halt, stop and page you. The lab agent never participates; the script is yours and runs where the key already is.
